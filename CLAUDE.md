# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project
CytoLex validates ISCN cytogenomic nomenclature strings (karyotype, FISH, microarray, …). Validation is **version-aware**:
- Results are given per ISCN edition (2016 now; 2020/2024 later — editions are not backward compatible).
- Every diagnostic cites the book (`ISCN 2016 §9.2.17.1, p.75, ¶1`).

Planned architecture: a UI-free core library, a desktop app (pilot UI), and later a web service reusing the library. App stack (T-020): **C# / .NET 10 LTS**. The core library uses a hand-written recursive-descent parser; the desktop app uses **Avalonia + AvaloniaEdit** with CommunityToolkit.Mvvm; tests use **xUnit v3**; the web service will use ASP.NET Core. The projects are scaffolded (T-024): `CytoLex.slnx`, `src/CytoLex.Core/` (UI-free library; embeds the KB bundle), `src/CytoLex.Desktop/` (Avalonia app), `tests/CytoLex.Core.Tests/` (xUnit v3 on Microsoft.Testing.Platform), `tests/CytoLex.Desktop.Tests/` (highlight mapping and view models of the desktop app, T-036), `src/CytoLex.External/` + `tests/CytoLex.External.Tests/` (external checkers, T-049); shared settings in `Directory.Build.props` (net10.0, nullable, warnings as errors, analyzers), package versions pinned centrally in `Directory.Packages.props`, SDK pinned in `global.json`, code style in `.editorconfig`. Core design (data model, version profiles, result/diagnostic API, fix model; KB read at runtime from a lean bundle embedded in the core): `docs/design/core.md` — follow it when writing core code. Full decision record: `docs/decisions.md`. Research notes: `docs/research/` (CytoGPS: `docs/research/cytogps.md`, T-047 — read it before working on T-048–T-052 or T-075; CytoLex vs. CytoGPS feature/accuracy comparison: `docs/research/cytogps-comparison.md` + `docs/research/data/cytogps-vs-cytolex-2016.csv` — update its "CytoLex today" column when a planned task listed there is done).

## Commands
Repo tooling is a **self-contained Python 3.14 project in `tools/`**, managed by **uv** (decision T-001). It's kept apart from the app code (see **App (.NET)** below).
- Layout: `tools/pyproject.toml`, `tools/uv.lock`, sources in `tools/src/cytolex_tools/`, tests in `tools/tests/`.
- Run every command from the repo root with `--directory tools` (or `cd tools` and drop the flag). If `uv` isn't on PATH, use `py -m uv …`.
  - Setup: `uv sync --directory tools`.
  - KB CLI: `uv run --directory tools kb <extract|tables|build|bands|ideograms|samples> [--version 2016]`, `kb check [PATH …]`, and `… kb <subcommand> --help`.
  - `kb check` validates rule/quote/vocab/translation YAML and the test corpus against `kb/schema/` (default: all of `kb/rules/`, `kb/source-quotes/`, `kb/vocab/`, `kb/translation/` and `tests/data/corpus/`); run it while writing KB files or corpus entries.
  - `kb build [--version 2016]` (default: every edition) runs `kb check` plus the cross-file and chunk checks (see `kb/README.md`), then writes `build/kb.sqlite`, `build/kb.json` (full KB), `build/kb-runtime.json` (lean runtime bundle for the core: rule metadata, vocab, bands from `kb/bands/<version>/bands.yaml`; format in `kb/README.md`) and `build/review/kb-review.md` (rules still needing review). Any error → exit 1, nothing written.
  - `kb bands [--version 2016] [--cache-only] [--update-pins]` downloads the pinned NCBI GDP ideograms (400/550/850) + UCSC cytoBand into `build/cache/bands/`, cross-checks them, compares them with the book's idiograms (`kb/bands/<version>/ideograms.yaml`), applies the cited `exceptions.yaml` and writes `kb/bands/<version>/bands.yaml` (committed; levels 300/700 come from the book). A sha256 mismatch (upstream change) → exit 1; re-pin deliberately with `--update-pins` and review the band diff. A book-vs-NCBI difference without an exception, or a stale exception → exit 1 and a draft of all differences in `build/review/bands/<version>/exceptions-draft.yaml`. Sources: `tools/src/cytolex_tools/bands/sources/<version>.yaml`.
  - `kb ideograms [--version 2016]` decodes the band labels of the book's idiograms (ISCN 2016 Fig. 5, pp.16–29) from the PDF text layer → `kb/bands/<version>/ideograms.yaml` (committed) + review crops in `build/review/bands/<version>/`. Config (pages, glyph map, spot-check sign-off): the `ideograms` section of the band sources file.
  - `kb samples [--version 2016]` writes batch sample files from the KB examples in `build/kb.json` to `tests/data/batch/<version>/` (committed, LF, byte-identical re-runs; format in `tests/data/batch/README.md`). Run it after `kb build` when examples changed; a C# test checks the `type` column against `Segmenter`. Book fragments and multi-line strings (seq results keep one part per line, T-019) are left out.
  - `kb tables` renders the configured table regions to PNG in `build/review/tables/<version>/` for the person sign-off of tables.
  - Tests: `uv run --directory tools pytest`; single test: `uv run --directory tools pytest tests/test_cli.py::test_help_lists_subcommands`.
  - Lint/format: `uv run --directory tools ruff check .` and `uv run --directory tools ruff format .`.

**App (.NET)** — requires the .NET 10 SDK; run from the repo root (the solution `CytoLex.slnx` is found automatically).
- **Prerequisite:** `build/kb-runtime.json`, `build/kb.json` and `build/kb.sqlite` must exist (`uv run --directory tools kb build`). The desktop app copies `build/kb.sqlite` to its output as `kb/kb.sqlite` for the rule browser (MSBuild property `CytoLexKbDatabase`; missing → build error "KB database not found"). `CytoLex.Core` embeds the lean runtime bundle `build/kb-runtime.json` as resource `CytoLex.Kb.bundle.json` (MSBuild property `CytoLexKbBundle`); the test projects embed the full `build/kb.json` (KB-example harness; desktop highlight checks over every KB example). - Build: `dotnet build`.
- Tests: `dotnet test` (Microsoft.Testing.Platform, opted in via `global.json`; VSTest-style `--filter` is not used).
  - It includes the **KB-example harness** (T-025, `tests/CytoLex.Core.Tests/KbExamples/`): one case per KB example (valid, invalid, `corrected`), read from `build/kb.json`, which the test project embeds. The validator is plugged in (T-028, `ValidatorAdapter`); invalid cases skip while their rule has no `[KbRule]` check in `CytoLex.Core` and the parser doesn't report it, and a `corrected` form must be a fix `Preview` of its rule's diagnostic when the KB fix is level 1 and the rule is implemented or parser-reported (T-035). Book fragments (`inv(2)`, `…` strings) are checked only for their own rule; a fragment of a rule that applies only to types the edition doesn't implement (seq's `g.4delT`) skips as not implemented (T-019). An invalid or corrected case whose string has no segment implemented in the pilot (e.g. ish-only examples of general rules) skips with the not-implemented reason (T-017). An invalid example whose own markers set a context outside its rule's (`rec` → constitutional for the neoplastic-only `REC.NOT_ACQUIRED`) is checked only with the matching hint (T-031). KB examples the core can't handle yet are listed with their task in `KbExamples/PendingExamples.cs`: their harness, parse and binder tests skip with that reason and fail once they pass, so remove the entry then (T-014). - **Remind the user to run commands.** Whenever a change makes a command necessary, tell them explicitly which command to run and why, in the step where it becomes necessary and again in the task's final report. Examples:
  - `uv sync --directory tools` after dependency changes;
  - `kb extract` after a fresh clone, a new edition, or an extraction-script or table-layout (`extract/tables/<version>.yaml`) change;
  - `kb ideograms` then `kb bands` after a decoder or `ideograms` config change; `kb bands` after an `exceptions.yaml` or band source change;
  - `kb build` after any KB edit (including a new `bands.yaml` from `kb bands`: bands go into the runtime bundle), or before running the app — then `dotnet build` so `CytoLex.Core` embeds the new bundle;
  - `kb samples` after a `kb build` that changed KB examples (batch sample files in `tests/data/batch/`).
- **Code standards (C#):**
  - **Avoid partial classes** (decided 2026-11-22, T-058). Don't split a hand-written class over several files to make it shorter; when a class grows too big, split it into smaller classes with explicit dependencies (e.g. a context object for shared state, one class per area). Exceptions: `partial` required by a source generator or framework, such as `[GeneratedRegex]`, CommunityToolkit.Mvvm `[ObservableProperty]`/`[RelayCommand]`, and Avalonia `*.axaml.cs` code-behind. The older hand-written splits (`Binder`/`Binder.Arr.cs`, `Parser`/`Parser.Arr.cs`) were restructured in T-083 (grammars over a shared `TokenCursor`/`GrammarBase`, binders over `BinderBase`).
- **Line endings: LF everywhere** (`.gitattributes` `* text=auto eol=lf`, T-055). Generators must write LF (`newline="\n"` / `write_bytes`); byte-compare tests rely on it.
- The tools resolve repo paths (`config/`, `kb/`, `build/`) from the repo root, not the working directory.
- ISCN PDF path: `config/local.yaml` (`iscn_pdf.<version>`), or env var `CYTOLEX_ISCN_PDF_2016` to override.

| `kb/vocab/<version>/` | Printed lists as parser vocabularies: ch. 3 symbols (`ch03/03-symbols.yaml`), Table 2 banding codes; `kb build` checks they cover every book row | Yes |

- **Citation anchors come from the chunks:** `[¶n p.N]` (prose paragraph) and `[En p.N]` (example block), numbered per numbered section; figures/tables carry their own label (`[Fig. 7 p.39]`, `[Table 1 p.12]`, `[Ploidy table p.90]`) and are cited by it. Cite as `ISCN 2016 §9.2.17.1, p.75, ¶1` or `… ¶2, ex. E3`; quote chunk text verbatim. See `manifest.yaml` for glyph mappings and conventions.
- **Before writing rules for a section, check `docs/extraction-review-2016.md`**: it lists what the text layer lost (drawn diagrams, shading, bold/italic) and which sections need `needs_review`. Chunk front matter flags `underlined` labels (U+0332 after an underlined character = homologue distinction) and `changed` labels (margin bar = changed since the previous edition).
- **Before writing KB files, read `kb/README.md`** (file layout, fields, vocabularies) and run `kb check` on them.
- **Rule IDs are stable concept IDs** (e.g. `TRANSLOC.CHROMOSOME_ORDER`) with a block per ISCN version. Don't rename IDs; add version blocks instead.
- **KB examples double as the test suite** for the validator and fixer.
- **Validation logic must trace to KB rules.** Don't encode ISCN rules from memory. If a rule is missing from the KB, add it (with a citation) first.
- **When writing rules, read only the relevant chunks** from `kb/source-text/`, not the whole PDF (token economy).

## ISCN source PDF
- The PDF lives **outside the repo**. Its path comes from `config/local.yaml` (gitignored; template `config/local.example.yaml`). Never commit the PDF or `kb/source-text/`.
- ISCN 2016: **book page = PDF page − 6**. Citations always use book pages.
- Extraction quirks:
  - `→` extracts as `]`.
  - Example strings may contain stray spaces (`t(2; 5)`).
  - Underlining (used to tell homologues apart) is recovered as U+0332 after the underlined character (T-003).
  - Ideograms (book pp. 16–29, Fig. 5) are drawings whose band labels use a figure-only font with private-use glyphs; `kb ideograms` decodes them (T-007). Band data = NCBI GDP + UCSC cytoBand (`kb bands`), checked against the book with a cited exceptions file.
